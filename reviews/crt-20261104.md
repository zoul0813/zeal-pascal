# Review crt-20261104: native Pascal CRT implementation

I reviewed the supplied diff and current files only. I did not build or run anything, and nothing in the material shows that any test has run. The findings below are ordered by priority. Items marked "verify" depend on hardware or kernel facts that the prompt does not include.

## Established defects and likely defects

**1. High (likely blocker; verify): MMU page readback in `crt_enter` may read the wrong page register**
- **Where:** `src/compiler_console.c`, `crt_enter`, sequence `crt_in(0xf1); push af; ld a,40h; out (f1),a`. `tests/native/crt.pas` `paint`/`sample` use the same `$DB/$F1` pattern.
- **Trigger and impact:** On Zeal 8-bit hardware, my recollection is that MMU registers are read back using the upper I/O address bits. With `IN A,(n)`, those bits come from A. Here A is `00` at the `IN A,(F1)`, because `LD A,0; OUT (8E),A` just ran. That would return virtual page 0's physical page, not page 1's. `crt_leave` would then write page 0's value into page 1. The runtime prefix in RAM mode, or page‑1 data in COM mode, would be unmapped on return from every ClrScr, ClrEol, InsLine and DelLine.
- **Evidence:** This rests on my recollection of the kernel's `MMU_GET_PAGE_NUMBER` convention (`ld a,page<<6; in a,(…)`), not on supplied files. The test oracles use the identical pattern. An emulator that decodes reads only by the low port byte would therefore pass both the helper and the test.
- **Fix or verification:** Compare against the kernel/platform MMU read macro and any existing page‑1 readback in this repository. If the convention is confirmed, emit `LD A,40h` before `IN A,(F1)` (or the canonical form), and fix the test inline code the same way. Add a test that maps page 1 to a page different from page 0 and checks it after each VRAM operation.

**2. Medium: Byte-typed arguments are probably rejected**
- **Where:** `crt_integer`, the check `cc_family(cc_expression())!=K_INTEGER → cc_fail(23)`.
- **Trigger and impact:** `K_BYTE` is a distinct family in `compiler.h`. If Byte variables report `K_BYTE`, then `var x,y:byte; GotoXY(x,y)` and `Delay(b)` fail with compiler error 23. TP3 accepts these, and they are very common in CRT programs. The spec text "Integer-family" also does not clearly exclude Byte.
- **Fix:** Accept Integer and Byte (and their subranges), using whatever predicate the other built-ins use. Add compile-and-run tests with Byte and Integer-subrange arguments.

**3. Medium: Delay does not save `RT_PC` across RST 8, and sleep errors are reported raw**
- **Where:** `crt_engine`, the `CRT_DELAY` branch.
- **Inconsistency:** Both existing syscall sites save and restore `0x40BE` around RST 8: `character` in `runtime.asm` and `stdout_flow`. Delay does not, so a checked sleep failure may report a stale source PC.
- **Error code:** Delay sends the kernel's A value straight to `RT_IOFAIL`. `IOResult` and the I+ report would then show a raw Zeal error number. Other physical paths map failures to a Pascal category (F0) and keep the native detail separately.
- **Fix:** Bracket the syscall with `LD HL,(RT_PC)/PUSH HL … POP HL/LD (RT_PC),HL`. Map the failure to a documented Pascal I/O code, storing the native detail as `character`/`file_cleanup` do. Update the spec sentence "Native sleep errors follow I+/I-" to name the code.

**4. Medium: The CrtInit snapshot lives in the code image and can outlive a run**
- **Where:** `cc.crt_state`, 9 bytes emitted into code.
- **Trigger and impact:** `harness-execute.c` treats native program mutations as part of the build ("mutations remain part of this build"). Suppose a RAM run ends between CrtInit and CrtExit through Halt, a runtime error or a user break. The active flag stays at 1. On a re-run of the same build, a CrtExit with no CrtInit in that run restores the previous run's registers. That violates the documented "no-op without prior Init".
- **Fix:** Clear the active byte at program start. A start hook, or a runtime-owned scratch byte that `start` zeroes, would both work. Add a test: Init, Halt, re-run, Exit, then check the registers are unchanged.

**5. Medium: Interrupts stay disabled for whole-screen operations**
- **Where:** `crt_enter`/`crt_leave` around ClrScr (two 3200-byte LDIRs) and InsLine/DelLine (up to 39 × 160-byte copies plus a blank).
- **Impact:** This is roughly 130k+ T-states, on the order of 10+ ms, with interrupts disabled. The PS/2 keyboard path may lose scancodes (for example, release sequences), causing stuck or missing keys. This interacts with the existing typeahead and flow-control machinery.
- **Fix:** Open an interrupt window per row or per chunk, restoring mapper and page 1 before EI and remapping after. Alternatively, document a measured bound. At minimum, record this as a known latency risk.

**6. Low–Medium: Out-of-range scroll registers can write outside VRAM**
- **Where:** `crt_row` (`A3+E`, a single `SUB 40`) and the ClrEol column (`A4+C`, a single `SUB 80`).
- **Trigger and impact:** If scrollY is 80 or more, which a user can set with `Port[$A3]`, the computed row exceeds `0x7FFF`. Writes then land in caller code at `8000+`. ADD can also overflow past 255.
- **Fix:** Reduce modulo 40/80 with a loop or mask, or confirm the register is hardware-bounded and say so in a comment.

**7. Low: The IFF2 capture via `LD A,I` has a known NMOS Z80 quirk**
- **Where:** `crt_enter`.
- **Impact:** If an interrupt is accepted during `LD A,I`, P/V reads 0. On NMOS parts, interrupts would then be left disabled after the helper.
- **Fix:** Confirm Zeal uses a CMOS Z84C00 and note this in the comment.

## Missing or weak tests

**8. High: GotoXY, LowVideo and ClrScr are never tested together with Write**
- `crt-main.c` redirects stdout to `CRT.TXT`. As a result, the core TP3 use case is untested: `GotoXY(10,5); Write('X')` should put X at that cell, in the LowVideo color.
- If the kernel's ZVB stdout driver keeps a RAM shadow of cursor, scroll or color, the direct register writes will diverge from it. GotoXY and LowVideo would then appear to work in the current tests while ordinary output ignores them.
- Two further cases need coverage:
  - ClrScr followed by Writeln down to row 40, to check that kernel scrolling stays coherent with scroll reset to 0.
  - A run with stdout not redirected, sampling VRAM after Write.

**9. Medium: The mapper-restoration check is vacuous**
- The test sets `port[$8E]:=0` at the start, then checks `port[$8E]=savedmap` (which is 0) after CrtExit. A helper that never restored 8E would pass.
- **Fix:** Set 8E to a nonzero bank before each CRT call, then verify it afterwards. Reset it to 0 only for the test's own register reads.

**10. Medium: Several documented contract points have no tests**
- Video mode ≠ 0 should give I/O 20, under both I+ (abort) and I- (`IOResult`), with no mapping changes.
- A caller with interrupts disabled must still have them disabled on return. The stage‑53 run executes with EI.
- Left-to-right, single evaluation of GotoXY arguments, for example with side-effecting functions.
- Repeated CrtInit replacing the snapshot.
- ClrEol at pending-wrap column 80, set via `Port[$A2]:=80`, changing no cells.
- Byte arguments (see finding 2).
- msleep with a pending error under I+ (abort path).
- `test_passed > 70` is a weak threshold; an exact count is preferable.

## Questions and verification requests

**11.** Does `msleep(0)` succeed in the kernel, or does it return an invalid-parameter error? The test would catch an error under I+, but the outcome should be confirmed and documented.

**12.** Is `cc` (including `crt_entries` and `crt_state`) zeroed for every compile and for every member, CHN or overlay group, within a single `compile_project`? If not, a cached entry from an earlier member would generate a call into foreign code. Also, if a first call site can lie inside an overlay member, the helper body lives in swappable code. Existing helpers appear to be emitted in `*_finish` phases, so this inline pattern is new.

**13.** Are ZVB cursor registers `A1`/`A2` visible coordinates, relative to scroll, as the code and test model assume? Or are they physical buffer coordinates? The emulator and the test share the same assumption, so a pass does not settle this for hardware.

**14.** CrtExit restores scroll and cursor without restoring screen contents. After a ClrScr, the program's final screen will display rotated by the old scroll offset. This matches the stated contract, but is it the intended user-visible result? Also, does the IDE re-establish its own colors, scroll and cursor after a run that called LowVideo or ClrScr without CrtExit? The spec requires IDE coherence.

**15.** This is minor: `crt_row` is emitted separately for each of ClrEol, InsLine and DelLine. One shared copy would save code space.

## Remaining findings

**A. Medium: the cursor-row register (`A1`) is not bounded before address calculation.**
- **Where:**
  - ClrEol: `IN A,(A1); LD E,A; CALL row`.
  - InsLine/DelLine: `IN A,(A1); LD D,A`.
  - `crt_row`: normalizes only scrollY, then adds E with a single `SUB 40`.
- **Trigger:** The A1 register value is 40 or more. The routine was hardened against raw `Port[$A3]` writes, so `Port[$A1]` deserves the same treatment. A1 could also be out of range if the board accepts such a value.
- **Impact on ClrEol:** E=100 with scroll 0 gives row 99, i.e. address `0x4000+7920`. That lies beyond the attribute plane, in other VRAM such as font or tile memory.
- **Impact on InsLine:** If D>39, E counts down from 39 through 0 and wraps past 255 until it equals D. Rows with E up to about 255 address past `0x7FFF`, which is the caller's own code.
- **Impact on DelLine:** If D>39, D increments, wraps, and copies through similar out-of-range rows.
- **Fix:** Either treat a row of 40 or more as a no-op (or I/O 20), or normalize modulo 40 the way scroll now is. Add one test, `Port[$A1]:=50; InsLine; DelLine; ClrEol`, that samples VRAM and checks the code pages are unchanged. If ZVB hardware guarantees A1<40, write that down in a comment and in the spec instead.

**B. Low–medium (verify): the board's single saved-cursor slot may be shared with the kernel.**
- CrtExit now restores the cursor solely through the A9 restore command, so A1/A2 are no longer restored explicitly.
- The spec forbids programs from touching the slot through `Port`. But if the kernel's ZVB stdout driver uses save/restore-cursor itself (for example ESC 7/8 handling or its own scroll path), an ordinary `Write` during a session would silently change where CrtExit returns.
- **Verification:** Confirm the pinned kernel never issues A9 bit 7 or bit 6. Add `CrtInit; GotoXY(…); Write('…'); CrtExit` to the existing cursor assertion, with stdout not redirected.

**C. Low (process): the evidence file records a failing Chain report.**
- `chain_component_and_activation` has `"passed": false`.
- The IDE-only replay covers the corrected `0068` PC lookup. However, no single run shows component, activation and IDE passing together with the current oracle.
- Rerun `tools/test-chain.py` in full and bind that report before claiming Chain acceptance.

**D. Low: the private-table count is hardcoded.**
- `package-native.py` checks `'<25H'` literally. The next private entry will need yet another manual edit.
- `len(metadata['private_input_addresses'])`, combined with a check against `RP_COUNT`, would be more robust. This is not a defect.

**E. Note: Chain activation ends any active CrtInit session.**
- A Chain from inside a CrtInit session leaves the display registers modified, and the child's CrtExit does nothing.
- This matches the documented per-program session rule. Mention it in the Chain section as well, so users pairing CrtInit/CrtExit across Chain are not surprised.
